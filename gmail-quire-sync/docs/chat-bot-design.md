# Google Chat のメッセージから Todo を作る：設計案

Chat スペースの投稿から「タスクらしいもの」を見つけ、人が確認してから Todo として登録する仕組みです。
目的の違う2つのトラックに分けて設計します。

| | トラック1：T-Consulting 内 | トラック2：汎用 Bot |
|---|---|---|
| 対象 | t-consulting.biz のメンバー（現在2名）、TC スペース | ドメインを問わない利用者・スペース |
| 登録先 | Quire（2名で完全共有） | Quire、Google ToDo リスト（Google Tasks）、カレンダーなど、差し替え可能 |
| 確認の届け方 | スペースのスレッドにカードを公開してよい | 本人にだけ届ける（DM など）。スペースには出さない |
| 基盤 | Workspace Studio ＋ 今の Apps Script（無料・既存の範囲） | Google Cloud（Chat アプリ、Cloud Run など） |
| 位置づけ | すぐ使う | トラック1で判定の質を確かめたあとに作る。将来、別の Bot にフォークできる形にする |

両トラックとも、候補のデータの形（登録ログの列）と「判定 → 候補 → 本人の確認 → 登録」の流れをそろえ、
トラック1で貯めた記録と判定の知見をトラック2に持ち込めるようにします。

---

## トラック1：T-Consulting 内（Studio ＋ Apps Script）

### 1-1. 全体の流れ

```
TC スペースの投稿 ─▶ Studio（Gemini：Chat 用スキル）─▶ Webhook ─▶ 受付口（GAS）─▶ 登録ログ（承認待ち）
                                                                            │
                     TC スペースの元メッセージのスレッドに確認カード ◀── 本体（GAS、5分ごと）
                                 │ ボタン（投稿者・担当者案の人・寺尾さんが押せる）
                                 ▼
                       承認ページ（GAS、t-consulting.biz 内に公開）─▶ Quire（担当者つき／なし）
```

### 1-2. Studio のフロー（2本）

| フロー | 開始条件 | 役割 |
|---|---|---|
| A. 自動 | 「チャット メッセージを受信したとき」／スペース: TC／絞り込みなし | 投稿を毎回 Gemini が判定し、タスクらしいものを候補にする |
| B. 合図 | 「絵文字のリアクションが追加されたとき」／🍀／スペース: TC／ユーザー指定なし | 誰かが 🍀 を付けたメッセージを必ず候補にする（AI の見逃しを拾う） |

- A が自分の投稿でも動くかを最初に確かめる。動かなければ自分の投稿は B で補う
- ペイロードは Gemini の出力に、Chat の変数（`source: チャット`、`message_id`、`chat_url`、`thread`、`sender`、`space`、`received_at`）を
  「項目名: 値」の行で添える。フロー B は `force: true` を足す

### 1-3. Chat 用スキル

メール用スキルをもとに「Quire タスク判定（Chat）」を作る。

- タスクにするもの：依頼（「〜お願いします」）、引き受け（「私がやります」）、決まった分担、期限つきの確認・提出
- タスクにしないもの：あいさつ、お礼、相づち、報告だけ（「送りました」）、雑談、予定の共有だけ、終わった作業
- 担当者：スキルにメンバー表（名前・呼び方・メール）を持たせ、宛先・メンション・引き受けた本人から推定。
  決まらなければ空（担当者なし）
- 迷ったら候補にして confidence を低くする（提案を優先）
- 出力：メール版の JSON に `assignee` を追加

### 1-4. 確認カードをスペースに返す

- TC スペースにも受信 Webhook を発行し、設定タブに「スペース → Webhook」の対応を登録する
  （Webhook の URL はスクリプト プロパティに置き、設定タブには名前だけを書く）
- チャット由来の候補は、元メッセージのスレッドに返信としてカードを送る（スレッドが分からなければスペースに新しく投稿）
- メール由来の候補は、今どおり寺尾さんの確認用スペースに送る

### 1-5. 承認ページを組織内に開く

- Web アプリの公開範囲を「t-consulting.biz 内の全員」に変える（実行は今どおり寺尾さん）
- ページを開いた人のアドレスを確かめ、次の人だけが操作できるようにする
  - メール由来の候補：寺尾さんだけ（今と同じ）
  - チャット由来の候補：寺尾さん、投稿者、担当者案の人
- リンクの署名はそのまま使う。組織外のアカウントでは開けない
- Quire への登録は、誰が承認しても寺尾さんの Quire 接続で行う（担当者はメールで指定）

### 1-6. 受付口・台帳・本体の変更

| 場所 | 変更 |
|---|---|
| 受付口 | `source: チャット` で V 列を「チャット」に。ID は `chat-` ＋メッセージ ID。Chat の URL を元リンクに許可。`force: true` なら必ず候補に |
| 登録ログ | AA 列「担当者」、AB 列「スペース」、AC 列「スレッド」を追加 |
| 本体：送信 | チャット由来はスペースの Webhook でスレッドに返信。カードに担当者案を表示 |
| 本体：承認 | 開いた人の確認（1-5）。担当者案で登録、空なら担当者なし |
| 本体：学習 | 送信者の学習はメールだけ（今のまま） |

## トラック2：汎用 Bot（Google Cloud）

### 2-1. 設計の考え方：部品を差し替えられる形にする

将来、別の Bot（別の判定対象、別の登録先、別の組織）にフォークしやすいように、
処理を「入口」「判定」「候補」「通知」「登録先」の5つに分け、それぞれを差し替え可能な部品（アダプター）にします。

```
 入口（Source）        判定（Detector）       候補（Candidate）      通知（Notifier）          登録先（Destination）
 ┌────────────┐      ┌───────────────┐     ┌──────────────┐     ┌──────────────────┐     ┌──────────────────┐
 │ Chat スペース │ ──▶ │ Gemini        │ ──▶ │ 候補の保管と  │ ──▶ │ 本人に DM カード  │ ──▶ │ Quire            │
 │ （将来: Gmail、│      │ （プロンプトと │     │ 状態管理      │     │ （将来: メール、  │     │ Google ToDo      │
 │  フォームなど）│      │  出力の型は設定）│     │ （Firestore） │     │  スペース内の非公開 │     │ カレンダー        │
 └────────────┘      └───────────────┘     └──────────────┘     │  メッセージ）      │     │ （将来: 他サービス） │
                                                                └──────────────────┘     └──────────────────┘
```

- 部品どうしは「候補」という共通のデータでつなぐ（項目はトラック1の登録ログと同じ意味）
- 判定のプロンプト、出力の型、通知の文面は設定ファイルに置き、コードを変えずに別の用途に流用できるようにする
- 利用者ごとの設定（使う登録先、既定のプロジェクトやリスト、通知の受け取り方）は利用者自身が Bot との DM で設定する

### 2-2. 全体の流れ

```
Chat スペース（Bot を追加したところ）
   │ Bot の追加 ─▶ そのスペースのメッセージ作成イベントを購読（Workspace Events API）
   │ 投稿
   ▼
Pub/Sub ─▶ Cloud Run「判定」：スレッド単位で数分まとめ、前後の文脈を Chat API で取得して Gemini で判定
                     │ 候補（タスク名・担当者案・期限・登録先案）を Firestore に保存
                     ▼
           Cloud Run「通知」：担当者案の人に DM で確認カード（担当者が決まらなければ投稿者へ）
                     │ ［登録する］［直して登録］［却下］（Chat アプリのカードなのでボタンがそのまま動く）
                     ▼
           Cloud Run「登録」：その人が接続した登録先（Quire／Google ToDo／カレンダー）に、その人の権限で登録
```

### 2-3. 本人に届ける方法（スペースに出さない）

| 方法 | 内容 | 条件・注意 |
|---|---|---|
| DM（第一候補） | Bot と本人の1対1のチャットに確認カードを送る | 本人が Bot を使える状態であること（本人が Bot を追加済み、または管理者が組織に一括でインストール済み）。初回に「接続」の案内も DM で送る |
| スペース内の非公開メッセージ | 元のスペースに「本人にだけ見える」メッセージとしてカードを出す | Chat アプリだけの機能。元の会話の近くに出せるが、作れる条件（どの場面で使えるか）を事前に検証する |
| メール | 確認リンクをメールで送る | DM が使えない相手（Bot を使えない組織外の人など）への予備 |

- 既定は DM。届けられないとき（Bot を使えない相手）は、候補を保留にしてスペースの Bot 管理者にだけ知らせる
- どの方法でも、確認・登録の操作は本人の Google アカウントで行い、本人以外は操作できない

### 2-4. 登録先（Destination）

| 登録先 | 接続の仕方 | 備考 |
|---|---|---|
| Quire | 利用者ごとに Quire の OAuth で接続 | プロジェクト・セクション・担当者を指定できる。トラック1のロジックを移植 |
| Google ToDo リスト | 利用者ごとに Google の OAuth（Tasks の権限）で接続 | 「カレンダーの ToDo」はこれ。リストと期限を指定 |
| Google カレンダー | 同上（カレンダーの権限） | 作業時間を予定として確保したい場合 |
| 将来 | 同じ「登録先」の型で追加 | Asana、Notion、Backlog など |

- 登録先の接続（OAuth）は、Bot の DM に出る「接続する」ボタンから行う。トークンは利用者ごとに暗号化して保管
  （Secret Manager または暗号化した Firestore）
- 利用者は既定の登録先を選べる。候補ごとにカードで変更もできる

### 2-5. ドメインをまたぐ場合

- 組織内だけで使うなら、Bot を組織内に公開し、管理者が一括インストールすれば DM がすぐ使える
- 他の組織の人も使えるようにするには、Google Workspace Marketplace に公開し、相手の組織の管理者に許可してもらう。
  OAuth の審査（使う権限の確認）が必要
- 組織外のメンバーがいるスペースでは、その人の投稿は判定するが、通知はその人が Bot を使える場合だけ届ける
- データは組織（ドメイン）ごとに分けて保存する

### 2-6. フォークしやすくするための約束ごと

- リポジトリは「共通部分（core）」と「アダプター（sources／detectors／notifiers／destinations）」と「設定（config）」に分ける
- 判定のプロンプトと出力の型は設定ファイルに置く（例：タスク判定、議事録からの決定事項抽出、問い合わせの分類）
- 候補の状態は共通（承認待ち → 登録済／却下／エラー）。判定の理由と結果を必ず記録し、学習や評価に使えるようにする
- 秘密情報はすべて Secret Manager。コードと設定ファイルには置かない
- インフラは Terraform などのコードで作れるようにし、別のプロジェクトにそのまま立てられるようにする

### 2-7. 費用と準備

- Cloud Run、Pub/Sub、Firestore は、この規模なら無料枠に収まる見込み。Gemini（Vertex AI）の利用料が少額かかる
- 準備：Google Cloud プロジェクト、Chat アプリの登録、Workspace Events API の有効化、
  スペース全投稿の読み取り権限についての管理者の承認、登録先ごとの OAuth クライアント
- Events API の購読には有効期限があるので、定期的に更新する仕組み（Cloud Scheduler）を入れる

### 2-8. 事前に検証すること

1. Bot（アプリの権限）でスペースの全投稿を購読できるか、そのために管理者の承認が要るか
2. スペース内の非公開メッセージにカードを出せる条件
3. 管理者が組織に一括インストールしたとき、Bot から各メンバーへ最初の DM を送れるか

---

## 進め方

1. トラック1を作る（Studio のフロー A・B、Chat 用スキル、受付口・台帳・本体の変更）
2. 2〜3週間使い、登録ログで判定の当たり外れと担当者推定の精度を見る
3. その結果（プロンプト、判定基準、よくある誤り）をトラック2の判定の設定として持ち込み、
   トラック2は「Chat → Gemini → DM → Quire／Google ToDo」の最小構成から作る
