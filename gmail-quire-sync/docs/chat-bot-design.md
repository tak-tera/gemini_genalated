# Google Chat のメッセージから Todo を作る：設計案

Chat スペースに投稿されたメッセージから「タスクらしいもの」を見つけ、メール版と同じ流れ
（台帳に承認待ちで追記 → 確認カード → 人が承認 → Quire に登録）に乗せる仕組みの設計です。
まず無料・既存の範囲（Workspace Studio）で始め、あとから他のスペースや他の人にも広げられる
Google Cloud 版に移れるように、両方を同じ台帳と受付口の形にそろえます。

## 前提（今回のスペース）

- メンバーは同じ組織の2名（寺尾さんともう1名）。2人とも Quire のアカウントがある
- タスクらしいメッセージは、どちらのメンバーからも投稿される（送信者で絞らない）
- 誰のタスクかは文脈から推定する。分からなければ担当者なしで登録してよい（登録の提案を優先）

## 1. Studio 版（無料・既存の範囲、まずこちらで始める）

### 1-1. フローは2本立て

| フロー | 開始条件 | 役割 |
|---|---|---|
| A. 自動 | 「チャット メッセージを受信したとき」<br>会話の種類: スペース／スペース: TC／絞り込みなし | 投稿を毎回 Gemini が判定し、タスクらしいものを候補にする |
| B. 手動の取りこぼし拾い | 「絵文字のリアクションが追加されたとき」<br>絵文字: 🍀（四つ葉のクローバー）／スペース: TC／ユーザー指定なし | 誰かが 🍀 を付けたメッセージを、必ずタスク候補にする（判定は担当者と期限の推定だけ） |

- A は、自分が投稿したメッセージでも動くかを最初に確かめる。「受信したとき」は他人の投稿だけで動く可能性がある。
  自分の投稿で動かなくても、B（自分で 🍀 を付ける）で補える
- B は送信者によらず使える。「これはタスク」と人が決めた合図なので、AI の判定より優先する
- 「自分の名前リンクが追加されたとき」（メンション）は、範囲が狭すぎるので今回は使わない。
  メンションされた依頼だけを拾う運用に切り替えたいときの選択肢として残す

### 1-2. フローの中身（A・B 共通）

```
Chat のきっかけ ─▶ Gemini に相談（Chat 用スキルで判定）─▶ Webhook の送信（受付口へ POST）
```

Webhook のペイロード（1行目は Gemini の出力、2行目以降は Chat のきっかけの変数。変数の名前は Studio の画面に合わせる）:

```
@（Gemini の出力）
source: チャット
message_id: @（メッセージ ID または名前）
chat_url: @（メッセージへのリンク。無ければ行ごと消す）
sender: @（送信者のメールアドレス）
space: @（スペース名）
received_at: @（投稿日時）
force: true        ← フロー B だけ（🍀 が付いたものは必ず候補にする）
```

### 1-3. Chat 用スキル（メール用スキルとの違い）

メール用の「Quire タスク判定」スキルをもとに、次を変えた「Quire タスク判定（Chat）」を作る。

- **タスクにするもの**：依頼（「〜お願いします」「〜しておいてもらえますか」）、引き受け（「私がやります」「明日までに送ります」）、
  決まった作業（「じゃあ資料は○○さん作成で」）、期限つきの確認・提出
- **タスクにしないもの**：あいさつ、お礼、相づち、報告だけ（「送りました」「終わりました」）、雑談、予定の共有だけ、
  すでに終わった作業
- **担当者（assignee）の推定**：スキルにメンバー表を持たせる（名前・呼び方・メールアドレス）
  - 依頼の宛先（「寺尾さん、〜を」）、メンション、引き受けた本人（「私がやります」の送信者）から決める
  - 決まらなければ空にする（Quire には担当者なしで登録）
- **短い発言**：1通だけでは文脈が足りないことが多い。判断がつかないときは is_task を true、confidence を低くして、
  人の確認に回す（提案を優先する方針）
- **出力**：メール版の JSON に `"assignee": "メールアドレス、または空文字"` を加える

### 1-4. 受付口と本体（Apps Script）の変更

| 場所 | 変更 |
|---|---|
| 受付口 | `source: チャット` を受け付け、V 列（出どころ）を「チャット」にする。ID は `chat-` ＋メッセージ ID。元リンクに Chat の URL（chat.google.com）を許可。`force: true` なら is_task が false でも候補にする |
| 登録ログ | AA 列「担当者」を追加（メールアドレス／空欄＝担当者なし）。メール由来の行は空のままで、今どおり設定の担当者（me）を使う |
| 本体：登録 | チャット由来の行は AA 列の担当者で登録する。空欄なら担当者なし |
| 本体：カード・編集ページ | カードに担当者案を表示し、編集ページの担当者欄に初期値として入れる |
| 本体：学習 | 送信者の学習はメールだけ（チャットでは送信者がメンバーなので、学習すると誤った振り分けになる）。今のまま |

確認カードと承認は今と同じく寺尾さんの確認用スペースに届く。もう1名の担当になるタスクも、寺尾さんが承認して登録する。

### 1-5. 最初に確かめること

1. 「チャット メッセージを受信したとき」が、自分の投稿でも動くか
2. きっかけの変数に、メッセージ ID（または名前）、メッセージへのリンク、送信者のアドレス、スレッドの情報があるか
3. スキルにメンバー表（スプレッドシートのタブ）を持たせたとき、担当者の推定が安定するか

### 1-6. Studio 版の限界

- フローは寺尾さん個人の設定。もう1名が自分用に使うには、その人も同じフローとスキルを作る必要がある
- 1通ずつの判定で、スレッドの前後の文脈は渡せない（Studio の変数にスレッドの履歴が無い場合）
- 対象スペースを増やすたびにフローの設定を直す

## 2. Google Cloud 版（汎用・複数スペース・複数人で使う）

### 2-1. 全体像

```
Chat スペース（Bot を追加したスペースならどこでも）
   │ メッセージ作成イベント
   ▼
Workspace Events API の購読 ─▶ Pub/Sub ─▶ Cloud Run（受け取り・判定サービス）
                                               │ ① スレッドの直前のメッセージを Chat API で取得
                                               │ ② Gemini（Vertex AI）で判定：タスクか／担当者／期限／登録先
                                               │ ③ 候補を台帳へ（スプレッドシート、または Firestore）
                                               ▼
                         Chat アプリ（Bot）が担当者案の人に DM で確認カード
                         ［登録する］［直して登録］［却下］ ← Chat アプリのカードなのでボタンがそのまま動く
                                               │
                                               ▼
                                        Quire API で登録（担当者つき／なし）
```

### 2-2. 部品

| 部品 | 内容 |
|---|---|
| Chat アプリ（Bot） | 組織内に公開し、誰でもスペースに追加できる。追加されたスペースを自動で対象にする |
| メッセージの受け取り | Workspace Events API でスペースの「メッセージ作成」を購読し、Pub/Sub に流す。Bot へのメンションだけでなく、スペースの全投稿を受け取れる |
| 判定サービス | Cloud Run（または Cloud Functions）。スレッド単位で数分まとめてから判定し、前後の文脈も Gemini に渡す |
| AI | Vertex AI の Gemini（Flash 系）。入力したデータが学習に使われない契約の範囲で使う |
| 設定 | スペースごとの設定（Quire の既定プロジェクト、メンバーと Quire アカウントの対応、確認の要否）をスプレッドシートか Firestore に置く |
| 確認と承認 | Bot が担当者案の人に DM で確認カードを送る。担当者が決まらないものは、スペースの管理者（設定で指定）に送る |
| Quire 連携 | 連携用の Quire アカウント1つで登録し、担当者はメールアドレスで指定する。トークンは Secret Manager に保管 |
| 台帳 | 今のスプレッドシートの形（登録ログ）を引き継ぐ。件数が増えたら Firestore に移し、スプレッドシートは閲覧用の写しにする |

### 2-3. Studio 版との違い

| | Studio 版 | Google Cloud 版 |
|---|---|---|
| 費用 | 追加なし（Workspace の範囲） | Cloud Run・Pub/Sub は無料枠内に収まる見込み。Gemini の利用料が少額かかる |
| 準備 | フローとスキルを作るだけ | Google Cloud プロジェクト、Chat アプリの登録、Events API の購読、管理者の承認 |
| 対象 | 設定したスペースだけ、寺尾さん個人 | Bot を追加したスペースすべて、メンバー全員 |
| 文脈 | 1通ずつ | スレッドの前後を含めて判定 |
| 確認 | 寺尾さんの確認用スペースに Webhook のカード | 担当者本人に Bot の DM カード（ボタンがそのまま動く） |
| 台帳・Quire 登録 | 今の Apps Script | Cloud Run に移す（ロジックは今の Apps Script を移植） |

### 2-4. 管理者として決めておくこと

- Chat アプリを組織内のどこまで使えるようにするか（全員／特定の組織部門）
- スペースの全投稿を AI に渡すことを、Bot を追加するスペースのメンバーにどう周知するか
- Vertex AI の利用リージョンとデータの保存場所
- Bot がスペースの全投稿を読む権限（アプリ認証での読み取り）を管理コンソールで承認するか。
  承認しない場合は、Bot を追加した人の権限で購読する形にする

## 3. 進め方

1. Studio 版のフロー A・B を作り、1-5 の3点を確かめる（ここで変数の名前が分かる）
2. 受付口・登録ログ（AA 列）・本体の変更を入れ、Chat 用スキルを作る
3. 2〜3週間使い、Chat からの候補の当たり外れを登録ログで見る（却下の割合、担当者の推定の正しさ）
4. 他のスペースや他の人にも使いたくなったら、その結果をもとに Google Cloud 版に進む
   （台帳の列と受付口の形をそろえてあるので、Studio 版から移っても記録はそのまま使える）
